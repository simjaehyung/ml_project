## 0. 중간발표 vs 최종발표 — 무엇이 달라지는가

| 항목 | 중간발표 (v13) | 최종발표 (v14 목표) |
|------|--------------|------------------|
| 앱 데모 | Streamlit mock 수준 | Next.js DSS + PMS 배포 수준 라이브 데모 |
| 시뮬레이션 | 50건 파일럿, 방향성만 | 전체 test set 기반 결과 (13,355건 목표) |
| 법률/한계 | 미포함 (교수님 지적) | 한국 숙박업 법령 + 악용 케이스 슬라이드 추가 |
| Phase 2 실험 | 미실행 | 날씨 ablation CI 포함 결과 제시 |
| Q&A 준비 | 슬라이드별 방어 포인트 | 교수님 재질문 예상 + 법률 질문 추가 |
| 발표 순서 | 문제 → 모델 → 시뮬 → 앱 | **앱 데모 먼저** → 모델 → 시뮬 → 법률 |

**최종발표 핵심 원칙 (lessons_from_mid_presentation.md 기반):**
- 핵심 메시지는 첫 슬라이드에
- 발표 첫 문장: "이 서비스는 누구에게 어떤 도움을 주기 위해 만들었는가"
- 숫자를 보여주는 것과 해석하는 것은 다르다 — 해석까지 발표자가 한다
- 한계를 먼저 드러내는 게 신뢰를 높인다

### Slide 02 — The Problem

**말할 내용:**
- City Hotel 취소율 41.7%, Resort Hotel 27.8% — Kaggle 119,390행 직접 계산
- "팔지 못한 시간은 영원히 손실" (perishable inventory)
- 기존 오버부킹의 문제: 손님이 체크인 당일에 통보받음

**핵심 수치:**
| 수치 | 출처 |
|------|------|
| 전체 취소율 37% | Kaggle Hotel Booking Demand 직접 계산 |
| City Hotel 41.7% | 동일 데이터셋 |
| Resort Hotel 27.8% | 동일 데이터셋 |

**예상 Q:** "€300+ 보상은 어디서 나왔나요?"
→ EU 항공 Denied Boarding Regulation 261/2004 참조 기준. 호텔은 법적 기준 없음 (→ 법률 슬라이드에서 상세히 다룸). 저희 시뮬레이션 결과(D: €46)는 ADR 기준 42% 수준.

### Slide 05 — Q1 증거: 모델 성능 (김나리 담당)

**말할 내용:**
1. 모델 비교 수치
2. Bootstrap 95% CI로 안정성 증명
3. 날씨 ablation 결과 — 솔직하게 보고

**핵심 수치:**

| 모델 | PR-AUC |
|------|--------|
| Dummy | 0.3870 |
| LR | 0.7818 |
| RF | 0.7785 |
| XGBoost | 0.8053 |
| **LightGBM ★** | **0.8189** [0.8128, 0.8245] |

Dummy 대비 **2.1배** (0.8189 / 0.387)

**날씨 ablation (먼저 한계 말하기):**
> "날씨 변수가 도움이 되는지 검증했습니다. 결과적으로 통계적으로 유의하지 않습니다."

| 조건 | PR-AUC | Bootstrap 95% CI |
|------|--------|-----------------|
| WITH weather | 0.8189 | [0.8128, 0.8245] |
| WITHOUT weather | 0.8166 | [0.8107, 0.8222] |
| 차이 | +0.0022 | CI 겹침 → 유의하지 않음 |

> "단, 날씨 피처 3개가 SHAP top-20에 등장하므로 모델이 활용하긴 합니다. 윈도우 확장(체류기간 전체) 실험을 Phase 2로 진행했으며 결과는 이 슬라이드에 업데이트 예정입니다."

**피처 중요도 Top 5 (gain):**
1. lead_time: 71,403
2. country_grouped_PRT: 62,520
3. total_of_special_requests: 29,285
4. previous_cancellations: 28,070
5. market_segment_Online TA: 21,037

**예상 Q:**
- "PR-AUC 0.819가 좋은 건가요?" → Dummy 대비 2.1배. Bootstrap CI가 좁고 안정적.
- "날씨가 도움이 안 된다면 왜 넣었나요?" → 모델이 활용하긴 함(top-20). "가정을 데이터로 검증하는 것이 이 프로젝트의 핵심이라 ablation 결과 자체가 기여."

### Slide 06 — Q2 근거: 왜 LLM인가

**말할 내용:**
> "협상 수락/거절 데이터가 0건입니다. 규칙 기반, 설문, 전통 ML — 어느 방법도 불가합니다."

| 방법 | 문제점 |
|------|--------|
| 규칙 기반 | 개인차 반영 불가 |
| 설문 | 가설적 응답 편향 |
| 전통 ML | 레이블 0건 |
| **LLM ✓** | 연구 문헌 기반 행동 시뮬 가능 |

**인용 논문:**
- Aher et al. (2023) — GPT-4가 경제 실험에서 인간과 통계적으로 유사한 분포 재현
- Horton & Argyle (2023) — normative hint 제거 방법론 근거

---

### Slide 07 — Q2 결과: 1,240 runs

**말할 내용:**
> "5개 아키타입 × 평균 6개 오퍼 구간 × 40회 반복 = 약 1,240 runs. Clopper-Pearson 95% CI로 검증."

**핵심 발견 2가지:**

**발견 1 — D 아키타입 Step Function (€46 임계값)**
| 오퍼 | 수락률 | CI |
|------|-------|-----|
| €29~€37 | 0% | [0.000, 0.088] |
| €46 | **100%** | **[0.912, 1.000]** |

→ €45 이하는 구조적으로 0%, €46에서 100%로 점프. CI 하한 91.2% → 강건.

**발견 2 — B 아키타입 앵커링 역설**
| 오퍼 | 수락률 | p값 |
|------|-------|-----|
| €91 | 100% | — |
| €99 | 0% | Fisher's exact **p < 0.000001** |

→ €99가 €91보다 높은데 수락률은 역전. Tversky & Kahneman (1974) 앵커링 이론과 일치.

**예상 Q:**
- "LLM 아티팩트 아닌가요?" → 가능성 인정. 통계적으로 p<0.000001로 유의하나 실제 인간 검증 필요. 실제 협상 데이터 수집 후 ML②로 검증이 목표.
- "normative hint 제거 이유?" → hint 포함 시 ceiling artifact 발생 확인. hint 제거 후 step function 회복. Horton & Argyle (2023) 방법론 준수.

### Slide 08 — 법률/한계 (김나리 담당)

**말할 내용 (교수님 지적 직접 대응):**

**Part 1 — 한국 법적 현황 (30초)**
> "교수님이 지적하신 법적 리스크를 조사했습니다. 한국 숙박업에는 항공과 달리 오버부킹을 금지하거나 의무 보상을 규정한 법이 없습니다. 소비자분쟁해결기준 30% 배상은 권고일 뿐 강제성이 없습니다."

| 구분 | 법적 지위 |
|------|---------|
| 항공 | 강제 보상 규정 있음 (국토교통부 고시) |
| 호텔/숙박 | 금지법 없음, 30% 배상 권고 (강제성 없음) |

**Part 2 — 우리 시스템이 리스크를 줄이는 이유 (20초)**
> "기존 오버부킹은 체크인 당일 사후 통보. 우리 Flexi는 예약 시점에 손님이 사전 동의하는 구조 — '계약 불이행'이 성립하지 않습니다."

**Part 3 — 쓰면 안 되는 케이스 (10초)**
> "단, 손님 동의 없이 강제 배정하거나 매니저 승인 없이 자동 라우팅하면 오히려 법적 리스크가 생깁니다. 그래서 '권장' 문구와 매니저 승인 단계는 제거할 수 없는 설계 요소입니다."

**예상 Q:**
- "한국에서 실제로 시행 가능한가요?" → 법적 금지 없음. 손님 동의 구조 갖추면 현행법 위반 없음. 다만 PMS 연동은 범위 외.
- "악의적으로 특정 손님을 Flexi로 몰 수 있지 않나요?" → 매니저 승인 단계 + "권장" 포지션으로 구조적 방지. 잘못 분류된 충성 고객은 매니저가 override 가능.

### Slide 09 — 시스템의 본질: 데이터 수집 인프라

**말할 내용:**
> "저희가 만든 것은 예측 모델이 아닙니다. 협상 데이터를 수집해서 더 나은 모델로 성장하는 인프라입니다."

```
Cold Start
  └─ 협상 이력 0건
  └─ LLM 시뮬 디폴트값 사용 (D: €46, B: ≤€91)
      ↓ 앱 운영
앱 협상 로그 축적
      ↓
ML② 학습 (이 호텔 전용)
      ↓
실시간 개인화 추천
```

| 구분 | ML ① (현재) | ML ② (미래) |
|------|-----------|-----------|
| 예측 대상 | P(취소\|예약피처) | P(수락\|예약피처, 오퍼금액) |
| 학습 데이터 | Kaggle 78,703건 | 이 호텔 협상 로그 |
| 상태 | ✅ 완료 PR-AUC 0.8189 | 수집 시작 후 가능 |

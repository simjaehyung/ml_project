```

    ↓
[앱] 취소 위험 예약 우선순위 리스트 (탭1) + 신규 예약 Flexi 라우팅 권장 (탭2)
```

우리가 증명하려는 것: **"이 데이터셋에서 취소 위험 우선순위화 접근법이 유효하게 작동한다"**

### Claim 1 이란?

> "LightGBM이 취소를 예측할 수 있다"

모델이 쓸 만한지를 숫자로 보여주는 파트.  
PR-AUC 0.8189 vs Dummy 0.3869 — **+112% 개선**이 핵심 수치.  
발표에서 김나리가 이 파트를 담당한다.

---

### Claim 2 란?

> "LightGBM이 예측한 취소 확률을 기반으로 Walk 보상 협상 전략을 설계할 수 있다"

Claim 1이 성립해야 Claim 2도 성립한다. 연결 고리가 이 프로젝트의 독자적 기여다.

**Walk(워크)가 뭔가?**  
호텔이 오버부킹됐을 때 체크인 당일 고객을 다른 호텔로 보내는 것.  
이때 호텔이 얼마의 보상금을 제시해야 고객이 수락하는가 — 이게 Walk 협상 문제.  
실제 데이터가 없으니 LLM 에이전트로 합성 레이블을 만들어서 분석한다.

**왜 아키타입 5종인가?**  
고객 유형마다 반응이 다르다. 가족은 아이 때문에 거부 가능성이 높고, 출장자는 상대적으로 유연하다.

| 아키타입 | 설명 | 특징 |
|----------|------|------|
| A — Business Solo | 1인 출장 | 거부감 낮음, 보상 기준 합리적 |
| B — Leisure Couple | 커플 여행 | 중간 |
| C — Family | 가족 여행 (아이 포함) | 거부감 높음, 높은 보상 요구 |
| D — Budget OTA | 최저가 OTA 예약 | 가격 민감하지만 유연 |
| E — Group | 단체 (12명+) | 협상 불가에 가까움 |

**Claim 2 방향성 체크 포인트:**  
`Family(C) 수락률 < Budget OTA(D) 수락률` — 이게 나와야 "아키타입별 반응이 다르다"고 주장할 수 있다.

---

### Walk 시뮬레이션이 왜 필요한가?

Flexi 할인율 공식 `5% + (위험점수 − 0.5) × 26%` 를 발표에서 제시할 때,  
"이 할인율이 실제로 효과 있냐?"는 질문이 반드시 나온다.  
시뮬레이션은 그 질문에 "LLM 에이전트 1,000회 시뮬레이션 결과 수락률 X%"라는 숫자로 답하기 위한 것이다.

**LLM 에이전트 구조:**
```
Hotel Agent (규칙 기반)
  → 오퍼 금액 제시 (ADR × 박수 × 30%)
      ↓
Customer Agent (LLM — 아키타입 페르소나 부여)
  → ACCEPT / COUNTER / REJECT (JSON 형식으로만 응답)
      ↓
Round 2 — 호텔이 반론 금액 조정 후 최종 수락/거절
```

**왜 vLLM과 Anthropic API 두 가지인가?**  
학교 서버(curie)의 GPU가 비어있으면 로컬 LLM(Qwen 14B)으로 무료 실행.  
GPU가 사용 중이거나 밤 이후에만 가능하면 Anthropic API(Sonnet 4.6)로 유료 실행.  
오늘 기준: API로 실행 중 (약 $2 소요), 밤에 vLLM으로 재확인 예정.

---

### 앱이 뭘 보여주는가

**탭1 — 기존 예약 우선순위 리스트**  
"오늘 체크인 예약 중 어느 것이 취소될 위험이 높은가"를 테이블로 보여줌.  
매니저가 고위험 예약을 클릭하면 SHAP으로 "왜 위험한가"를 설명.

**탭2 — 신규 예약 Flexi 라우팅**  
신규 예약 정보 입력 → 취소 확률 예측 → 임계값(0.60) 초과 시 Flexi 풀 라우팅 권장.  
Flexi = 변경 가능 요금제. 취소 위험 고객을 미리 유연한 요금제로 유도해 빈 방 손실 줄이기.

## 2. 파일럿 결과 확인 (60회, A·D 아키타입)

```
아키타입 A (Business Solo, ADR €120, 2박)
  초기 오퍼 €62  → 수락률 60%
  초기 오퍼 €101 → 수락률 60%
  초기 오퍼 €144 → 수락률 40%

아키타입 D (Budget OTA, ADR €55, 2박)
  초기 오퍼 €29  → 수락률 60%
  초기 오퍼 €46  → 수락률 50%
  초기 오퍼 €66  → 수락률 50%

JSON 파싱 성공률: 100%
```

### 파일럿에서 주목할 점

**[OK]** 파싱 성공률 100% — 프롬프트 구조 문제없음  
**[OK]** 오퍼 금액 올라갈수록 수락률 하락 — 단조성 확인  
**[주의]** A와 D 수락률 거의 동일 — 지금은 파일럿(10회/셀)이라 샘플 부족, 전체 40회/셀로 재확인 필요  
**[확인 필요]** `counter_mean = 120.0` (A·D 동일) — 카운터 제안 금액이 ADR값에 묶이는 버그 가능성, 전체 결과 나오면 검토

### Claim 2 방향성 체크 기준
> Family(C) 수락률 < Budget OTA(D) 수락률이어야 Claim 2 방어 가능  
> 파일럿에는 C·E가 없음 — **전체 결과 나올 때까지 판단 보류**

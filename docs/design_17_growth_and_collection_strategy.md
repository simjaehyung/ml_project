## 0. 한 줄 요약

> **우리는 "다른 호텔에서도 잘 맞추는 모델"을 만드는 게 아니라, "우리 호텔 데이터가 적은 데서 많은 데로 쌓일수록 자라는 시스템"을 만든다.**
> 그 성장을 (I) 실데이터로 정량 증명하고, (II) 하이쿠 손님으로 "세상에 없는 협상 데이터가 실시간 수집되는 장면"을 시연한다.

## 1. 핵심 프레임 전환 — 무엇을 증명하는가

| 버린 목표 (공격받음) | 채택한 목표 (방어됨) |
|---|---|
| "이 모델이 현실(다른 호텔)을 잘 맞춘다" | "이 **시스템**이 *우리* 데이터가 쌓일수록 자란다" |
| 평가 = 정확도 절대값 | 평가 = **성장 곡선 + 구간별 최적 모델** |
| 일반화 (CLAUDE.md상 애초에 목표 아님) | 도메인 적응 / 콜드스타트 → 성장 |

CLAUDE.md 명시: **"일반화 목표: 없음."** 따라서 "우리 호텔 데이터로 어떻게 성장하는가"가 정확히 프로젝트 정의에 부합한다.

추가 사실: Kaggle 데이터는 "남의 호텔"이 아니라 **우리가 다루는 그 두 호텔(City=리스본, Resort=알가르브)의 실제 2년치 기록**이다. 따라서 "우리 호텔 데이터가 쌓이며 자라는 곡선"을 **하이쿠 없이 실데이터 시간순 스트리밍으로 바로 그릴 수 있다.**

## 2. 두 트랙 (역할 분리)

| 트랙 | 무엇 | 데이터 | 하이쿠 | 주장 성격 | 상태 |
|---|---|---|---|---|---|
| **(I) 취소모델 성장 + 구간별 모델선정** | 데이터 쌓일수록 PR-AUC 자람 / 구간별 최적 모델 교체 | 실 Kaggle 시간순·비율 스트리밍 | ❌ 미사용 | **정량(방어 담당)** | 설계 확정, 실험 미실행 |
| **(II) 협상 데이터 수집 라이프사이클** | (위험도→오퍼→수락→취소) 튜플 실시간 수집 | 하이쿠 생성 | ✅ 유일 부트스트랩 | **시연(차별화 담당)** | 설계 진행 중 |

**오염 금지 원칙:** (I)은 순수 실데이터, (II)는 순수 합성. **하이쿠 데이터를 리스본 취소모델(I)에 절대 섞지 않는다** — 분포 불일치(distribution shift)로 모델이 망가진다.

## 3. 확정된 결정들

1. **LightGBM 0.8189을 버리지 않는다.** 격하가 아니라 **성장 곡선의 day-0 앵커 / full-data 최적점**으로 재배치. Bootstrap CI·날씨 ablation까지 방어된 유일한 무조건 방어 자산.
2. **하이쿠로 리스본 취소모델을 재학습하지 않는다.** (3절 오염 금지) 하이쿠가 리스본 손님을 모방하면 모델이 오히려 이상해진다 — 팀 합의.
3. **하이쿠는 협상(ML②)에 건다.** 협상 데이터는 실제로 0건 → 시뮬이 유일 수단 → 순환논리 없음. "격하시킬 기존 모델"이 없는 유일한 자리.
4. **취소 라벨 생성은 P1(하이쿠 자가취소) 채택.** 비측정성은 감수 — 이 트랙의 산출물은 *정확도 숫자*가 아니라 *수집 시연*이라서 치명타 아님.
5. **주장 범위 규율(scope discipline):**
   - 정량 성장 주장 → **트랙 I(실데이터)에만.**
   - 협상 트랙 → **"수집 시연" + 기존 Slide 07 정량 숫자 재사용.** 새로 만든 라이프사이클이 1,240 runs 결과를 부정/변경하지 않는다.
   - 자가취소 행동을 우리가 설계하므로 결과가 자기실현적임을 **명시적으로 선언** → "현실 증명이 아니라 운영 데이터 수집 인프라 시연. 현실 검증은 실배포 로그의 몫."

## 4. 큰 과제 — 모델 선정을 데이터량의 함수로 (트랙 I 확장)

### 4.1 통찰

우리는 적은 데이터 → 많은 데이터로 가는 시스템이다. 그렇다면 **LightGBM 하나로 고정하는 것 자체가 가정 오류**다. 데이터 구간마다 최적 모델 클래스가 다르다:

- **적은 데이터:** 단순·고편향 모델(LR 등)이 과적합이 덜해 유리할 수 있음
- **많은 데이터:** 부스팅(LightGBM/XGBoost)이 비선형을 잡아 역전

→ 성장하는 시스템은 모델을 **고정하지 말고 데이터량에 따라 재선정**해야 한다. "어느 구간에선 누가 좋고 어느 구간에선 누가 좋은가"를 **캐글 실데이터로** 밝힌다.

### 4.2 실험 설계 (실데이터, 순환논리 0)

```
학습량 비율 = {1%, 5%, 10%, 25%, 50%, 100%}   (또는 시간순 1·3·6개월…) 사용자 의견 : 주 단위로 학습하는걸로 해보자
모델        = {Dummy, LR, RF, XGBoost, LightGBM}
고정 평가셋  = 기존 시간기반 test split (마지막 6개월)
지표        = PR-AUC + Bootstrap 95% CI
산출물      = x=학습량, y=PR-AUC, 모델별 5개 곡선 → 교차점(crossover) 표시
```

재사용 자산: `src/preprocessing_pipeline.py`, `src/run_all_models.py` (또는 기존 모델 비교 코드)를 **데이터 비율 루프로 감싸기만** 하면 됨. 신규 코드량 작음.

### 4.3 통계적 주의 (필수)

- 적은 N에서 PR-AUC 추정은 노이즈가 크다. **CI가 분리될 때만** "이 구간은 모델 X가 우월"이라 주장.
- CI가 겹치는 교차점은 "교차"라 부르지 않는다 — Slide 05/07에서 지킨 동일 기준(Bootstrap CI, Clopper-Pearson) 유지.

### 4.4 발표 임팩트

기존 Slide 05(full-data 모델 비교표)를 **"데이터량에 따라 승자가 바뀐다"는 동적 그래프**로 격상. "우리는 모델을 고르지 않는다 — 데이터가 모델을 고르게 한다"는 메시지는 성장-인프라 thesis를 직접 강화. LightGBM 0.8189는 full-data 구간 승자로 그대로 살아있음.

## 5. 하이쿠 협상 라이프사이클 설계 (트랙 II)

### 5.1 3단계 + 수집 튜플

```
Phase 1 — 예약 (거의 구현됨, "생각" 노출만 추가)
   하이쿠가 손님으로 추론 → PMS → DSS 위험도 산출
   수집: 예약피처 + risk_score

Phase 2 — 협상 (★ 현재 빠진 핵심 전제)
   DSS 고위험 판정 → PMS가 하이쿠에게 Flexi "제안":
   "X% 할인 + 7일 전 무료취소, 단 취소 시 객실은 대기손님에게. 받으시겠습니까?"
   하이쿠가 design_10의 4단계 숙고 → 수락/거절
   수집: (risk_score, 할인율, 수락여부)  ← ML② 학습 데이터의 실체

Phase 3 — 자가취소 (★ P1, 루프 닫기)
   시간 경과/교란(회의 연기·날씨 악화·더 싼 곳) 부여 → 취소/유지 결정
   Flexi 수락자 = 통보 후 취소(객실 회수) / 미수락자 = 막판 취소·노쇼
   수집: (…, 취소여부, 통보일수)  ← walk-rate 검증 가능
```

**누적 코퍼스 = (위험도 → 오퍼 → 수락 → 취소) 완전 튜플 = 세상에 없는 데이터 = 차별화의 실체.**

### 5.2 현재 코드 갭

지금 `agents.py`는 예약 시 PMS가 `pricing_type`을 **이미 결정해 통보**한다 → 협상이 아님. **Flexi를 "결정"이 아니라 "질문"으로 바꾸는 것**이 Phase 2의 첫 단추. Phase 2 없이는 Phase 3의 "Flexi 수락자는 다르게 취소한다" thesis가 성립 불가 → **Phase 2·3은 한 묶음.**

### 5.3 발표 포지션

```
Slide 07 (기존)   = 수집된 협상 데이터 분석 → D €46 step function (정량)
하이쿠 라이프사이클 = 그 데이터가 지금 한 건씩 들어오는 라이브 장면 (수집)
```
→ **보완 관계. 대체 아님.**

## 8. 발표 통합 그림 (현실 버전)

```
(I)  실데이터 성장 곡선 + 구간별 최적 모델   → 정량 증거 (방어)
하이쿠 라이브: 손님이 생각하며 예약·협상·취소 → "데이터 유입" 라이브 (차별화)
(II) 호텔 A 콜드스타트                       → 개념 서술 (낭만, 풀빌드는 미래)
```

- 정량은 실데이터가 책임진다.
- 차별화(협상 데이터 수집)는 하이쿠 라이프사이클이 보여준다.
- LightGBM 0.8189은 버려지지 않고 full-data 구간 승자 + 곡선 앵커로 남는다.

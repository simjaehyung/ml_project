## 주장 1 — LLM의 제로샷 취소 예측

### 검증 파이프라인

예약 데이터를 자연어로 직렬화해서 LLM에 그대로 던진다.

```python
prompt = """
A hotel guest made a booking with the following details:
- Country: {country}
- Booking channel: {market_segment}
- Days before check-in: {lead_time}
- Special requests: {total_of_special_requests}
- Parking required: {required_car_parking_spaces}
- Average daily rate: €{adr}
- Previous cancellations: {previous_cancellations}

What is the probability (0.0 to 1.0) that this booking will be cancelled?
Answer with a single number only.
"""
```

- 입력: 테스트셋 (2017-01 ~ 2017-08, 40,687건)
- 모델: Qwen2.5-14B (로컬, A5000 × 2)
- 출력: 취소 확률 0.0 ~ 1.0
- 평가: PR-AUC, F1@0.5

### "괜찮은 성능"의 기준

| 모델 | PR-AUC | 비고 |
|---|---|---|
| Dummy | ~0.37 | 취소율 = 기저선 |
| LR Baseline | ~0.75 | Week 2 결과 |
| LGBM (우리 모델) | 0.8189 | Week 3 확정 |
| **LLM Zero-shot** | **측정 예정** | 훈련 없음 |

LLM이 Dummy를 유의미하게 넘으면 "LLM이 이 도메인을 이해한다"는 증거가 된다.

## 주장 2 — Walk 보상 협상 시뮬레이션

### 왜 LLM이 필요한가

오버부킹 walk 협상 결과는 Kaggle 데이터에 없다.
실제 호텔이 walk 협상을 기록하기 시작해야 쌓이는 레이블이다.
그 레이블이 없는 현재, LLM이 고객 역할을 해서 합성 레이블을 생성한다.

### 5개 아키타입 (Kaggle 피처로 도출)

모든 피처는 표준 PMS 예약 데이터에서 그대로 수집 가능.

| 아키타입 | 핵심 피처 조합 | Walk 난이도 |
|---------|-------------|-----------|
| A: 비즈니스 솔로 | Corporate, adults=1, 1~2박 | 낮음 — 대안 수용력 높음 |
| B: 레저 커플 | Online TA, adults=2, 주말 체류, 중간 ADR | 중간 |
| C: 가족 | children>0, HB/FB, 장박 | 높음 — **마지노선** |
| D: 예산형 OTA | Online TA, 저 ADR, special_req=0 | 낮음 — 금액에 직접 반응 |
| E: 단체 | Groups, 10인+ | 매우 높음 — 대표자 협상 필요 |

### Layer 2 — Walk 우선순위 규칙 (LLM 개입 없음)

오버부킹 N실 발생 시 Flexi 풀에서 Walk 대상 선택:

```
1순위: 가장 낮은 ADR
2순위: 단기 체류 (1~2박)
3순위: 특별 요청 0개
마지노선: 아키타입 C (가족) 제외
```

### 협상 구조 — 다중 에이전트 2라운드

```
[Hotel Agent — 규칙 기반]
  초기 오퍼: ADR × nights × 0.30
  예산 상한: ADR × nights × 0.60
  Round 2 조정: min(counter_amount × 0.85, 예산 상한)

[Customer Agent — LLM]
  아키타입 프로파일 + 상황 맥락 주입
  출력: {"decision": "ACCEPT|COUNTER|REJECT", "counter_amount": 숫자|null}

[Round 흐름]
  Round 1: Hotel 초기 오퍼 → Customer 반응
  Round 2: Hotel 조정 오퍼 → Customer 최종 결정
  JSON 출력 강제 — 환각 차단
```

Hotel Agent는 규칙 기반으로 고정. LLM은 Customer Agent만 담당.

### 시뮬레이션 설계

- 아키타입 5개 × 보상 금액 구간 5개 = 25개 조합
- 조합당 40회 반복 = 총 1,000회
- 출력: 조합별 수락률

```
보상 구간 (nights=2, ADR=€95 기준):
  구간 1: €50   (ADR × nights × 0.26)
  구간 2: €80   (ADR × nights × 0.42)
  구간 3: €114  (ADR × nights × 0.60) ← 예산 상한
  구간 4: €140  (예산 상한 초과 — 거절 기준선 확인용)
  구간 5: €170  (명확한 거절 예상 — 베이스라인)
```

### 효용 증명 방법

아키타입 C(가족)의 수락 임계값 > 아키타입 D(예산형)의 수락 임계값이면:
→ "아키타입이 다르면 최적 오퍼가 다르다" = 가이드라인이 의미 있다

기대 산출물:

| 아키타입 | 권장 초기 오퍼 | 예상 수락률 | 예산 상한 |
|---------|-------------|-----------|---------|
| A (비즈니스) | ADR × 0.30 | ~85% | ADR × 0.50 |
| B (레저 커플) | ADR × 0.45 | ~75% | ADR × 0.65 |
| C (가족) | Walk 비권장 | — | — |
| D (예산형) | ADR × 0.25 | ~90% | ADR × 0.45 |
| E (단체) | 별도 협상 | — | — |

## 3단계 로드맵 — 궁극의 모델 형태

```
Stage 1 (현재 — LLM 시뮬레이션)
  Walk 레이블 없음
  LLM이 합성 레이블 생성
  → 초기 가이드라인 도출

Stage 2 (DSS 운용 중 — 하이브리드)
  실제 walk 협상 데이터 누적
  LLM이 빈 구간 채우고 실제 데이터가 검증·보정
  → 가이드라인 정밀도 향상

Stage 3 (궁극 — 순수 ML)
  P(수락 | 고객 피처, 보상금액) 예측 모델
  LightGBM 학습 가능 수준의 walk 레이블 확보
  LLM 시뮬레이션 대체
  → 실시간 최적 오퍼 계산
```

LLM 시뮬레이션은 Stage 3 ML 모델이 작동하기까지의 브릿지다.

## 전체 방어 논리 요약

```
[주장 1 성립]
  LLM zero-shot PR-AUC > Dummy
    → LLM이 호텔 예약 취소 행동을 이해한다는 경험적 근거

[주장 1 → 주장 2 연결]
  LLM이 호텔 도메인을 이해한다면
  아키타입을 부여했을 때 walk 협상 반응도 도메인을 반영한다

[주장 2 성립]
  아키타입별 수락 임계값 분포가 통계적으로 다름
    → 세그먼트별 최적 오퍼 가이드라인이 의미 있다

[결합 주장]
  이 시스템은 호텔이 실제 walk 사례 없이
  아키타입별 보상 전략을 사전에 설계할 수 있게 한다
  데이터가 쌓이면 Stage 3 ML로 대체된다
```

## 예상 공격 Q&A

| 공격 | 방어 |
|---|---|
| "LLM이 진짜 고객처럼 생각하냐?" | "훈련 없이 테스트셋에서 PR-AUC X.XX가 나왔습니다. 이론이 아닌 숫자로 도메인 이해를 먼저 보여드립니다." |
| "walk 협상 결과를 어떻게 믿냐?" | "정확한 수치를 주장하는 게 아닙니다. 가족이 예산형보다 더 높은 보상을 요구하는 방향성이 상식과 일치하는지 확인하는 탐색 도구입니다." |
| "아키타입이 실제 고객과 다르면?" | "아키타입은 2년치 실제 예약 데이터의 표준 PMS 피처로 도출됩니다. DSS 운용 후 실제 고객 분포로 calibration됩니다." |
| "왜 LLM이냐, 설문 하면 안 되냐?" | "설문은 가상 답변 편향이 있습니다. Stage 3에서는 실제 walk 데이터가 쌓이면 ML로 대체됩니다. LLM은 그때까지의 브릿지입니다." |
| "호텔 에이전트도 LLM이냐?" | "아닙니다. 호텔 에이전트는 규칙 기반입니다. 불확실한 것은 고객 반응뿐이므로 LLM은 Customer Agent만 담당합니다." |

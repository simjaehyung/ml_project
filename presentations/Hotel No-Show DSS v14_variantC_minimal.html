예측 모델이 아니라,
데이터로 자라는
의사결정 인프라를 만들었습니다.

호텔에 핏한 예약 데이터를 효과적으로 수집하고, 그 데이터로 자라는 ML 예측(오버부킹 · 그 외 도메인)을 통해 수익과 경영 안정성을 극대화하는 데이터 수집 인프라.

첫 문장 "우리가 호텔에 파는 건 모델 한 개가 아니라, 쓸수록 똑똑해지는 인프라입니다."

01 · 데이터가 들어온다

여러 플랫폼의 예약이 모인다 — 각 예약은 수십 개 피처를 가진 한 점

DirectOnline TAOffline TA/TOCorporateGDS → 우리 PMS(예약 앱)가 한 곳으로 수집
정상 취소 각 점 = lead_time · 국적 · 요청수 · 채널 · ADR … 수십 개 피처
멘트 "예약 하나하나가 곧 데이터입니다. 흩어진 플랫폼의 예약이 우리 인프라로 모입니다 — 이게 수집구입니다."
02 · 작동 증거 ① · 정량 핵심

데이터가 쌓일수록 모델이 자란다 — 데이터가 모델을 고른다 국적 피처 윤리 → S11

실데이터(Kaggle · 우리 두 호텔의 실제 2년 기록) · 누적창 79주 · Bootstrap 95% CI · 하이쿠 미사용
  • 콜드스타트(데이터 거의 없음)에선 단순모델(LR)이 우위 — 빠르게 올라 plateau
  • 약 5.4만 건(W)에서 LightGBM이 통계적으로 추월 → 끝까지 유지
  • 그 사이 구간은 구분 불가(tie) — CI가 겹치면 "교차"라 부르지 않는다
  • full-data 최종 PR-AUC 0.820 (Dummy 0.387 대비 2.1배)

"성장형 시스템은 모델을 고정하지 않는다 — 데이터량이 최적 모델을 정한다."

멘트 "정적 비교표가 아니라, 데이터가 쌓이며 승자가 바뀌는 동적 곡선입니다. 이게 인프라의 핵심 약속입니다."

03 · 의사결정

위험도에 따라 몇 개를 오버부킹할 것인가

입력

10건의 취소 위험도 분포 (고위험 4건)

결정 원리

한계비용 = 한계수익 지점에서 최적 오버부킹 (호텔 RM 표준)

결정

위험 기반으로 4실 오버부킹 가정

  • 업계 관행: 객실의 5~15% (비즈니스 10–15% · 레저 5–10%)
  • risk-based 방식이 RevPAR가 더 높다는 연구 — 우리 접근의 근거
  • 결정 권한은 매니저가 보유 (자동화 아님 · GDPR Art.22)
멘트 "오버부킹 수준은 우리가 지어낸 게 아니라 교과서적 RM 결정법입니다. 우리는 거기에 위험도 예측을 붙였습니다."
03 · 기대 효과

오버부킹 K에 따른 기대 이익 곡선 가정 아님 · 실데이터 기대값

E[순이익(K)] = 채운 방 수익 − E[walk 보상 · 평판 비용] · 모델 위험도 기반 기대값 (sim_hotel.py)
  • K가 적으면 빈 방 손실 (perishable · 회복 0)
  • K가 많으면 walk 보상 + 평판 손실
  • 두 비용의 균형점이 최적 오버부킹

비용비(빈방:walk)는 미지수 → 범위 sweep으로 제시. 평판 포함 시 walk가 더 비싸 비용비가 거꾸로일 수 있어 → 보수적 오버부킹이 정답.

정직 (pin) "이 곡선은 가정이 아니라 우리 모델의 위험도로 계산한 기대값입니다 — 근거는 바로 이어집니다."
03 · 예측이 틀렸다

예측 하나가 빗나가 보상이 필요한 상황

고위험으로 분류된 손님이 실제로는 체크인 → 오버부킹 충돌 → 손님을 다른 호텔로 이전(walk).

업계 walk 보상 표준법적 지위
동급/상위 호텔 + 첫날 숙박비 + 교통비 + 굿윌(포인트·바우처)규제 없음 — 선불 환불만 의무 (항공과 다름)

브랜드 예시 · Hyatt 첫날 + 교통 + 전화 · Marriott 상한 $200 + 14만 pts · 럭셔리 $200 + 9만 pts

멘트 "예측은 틀릴 수 있습니다. 중요한 건 틀렸을 때 마찰을 어떻게 최소화하느냐 — 그게 다음 도메인입니다."
03 · 보상 정책

페르소나가 아니라 체계화된 피처로 가격대를 찾는다

가격대를 정하는 두 힘

  • 하한 — 손님 만족 (너무 낮으면 불만)
  • 상한 — 평판 비용: 별점 1↓ = 매출 5~9%↓, 부정리뷰 3건+ → 79%가 예약 안 함

피처 → 보상 차등 (근거 있음)

  • 인원수 多 → 대체 숙소 확보 난이도↑
  • 예약 임박 → 대안 부족 → 불만↑
  • 등급/채널 → 로열티별 차등 (브랜드 실재)
  • 국적은 차등에서 배제 (차별 방지)

1차 증거: walk 협상 시뮬 D 아키타입 €46 (≈ ADR 42%) — 업계 보상과 같은 자릿수.

멘트 "우리는 손님을 캐릭터로 안 봅니다. 인원·예약시점·세그먼트라는 피처로 적정 가격대를 찾습니다."

04 · 왜 믿을 수 있나집중 정산 블록

의심에 정면으로 답한다 — 윤리 · 법률 · 효과

윤리 — 국적 차별

국적이 위험도 1위 피처. → 예측엔 쓰되 행동 차등엔 배제. ablation으로 성능비용 측정 + is_domestic 검토. 사전동의·매니저 승인 필수.

법률 — 우회로

한국 숙박업은 오버부킹 규제 공백. 우리 Flexi는 예약 시점 사전 동의 구조 → '계약 불이행'이 성립 안 함. 강제 배정·자동 발효는 금지선.

효과 — 시뮬 ≠ 현실

정량 주장은 실데이터가 책임(성장곡선). 협상 시뮬은 "수집 인프라 시연"이지 현실 증명 아님. 현실 검증은 실배포 로그의 몫 — 정직하게.

멘트 "앞에서 핀으로 찍어둔 의심들을 여기서 정산합니다. 한계를 먼저 드러내는 게 신뢰를 높입니다."
05 · 비전

오버부킹은 첫 도메인일 뿐

같은 수집 인프라가 여는 예측 도메인:

수요·인력

도착 예측 → 인력 배치

데이터가 쌓일수록 모델이 자라고(성장곡선), 수집 영역이 넓어질수록 도메인이 늘어난다. 쓸수록 똑똑해지는 인프라.

멘트 "취소예측 앱이 아닙니다. 한 번 깔면 여러 도메인으로 자라는 데이터 인프라입니다."
결론

3줄 요약

1

수집 인프라 — 호텔에 핏한 예약 데이터를 모아 ML 예측으로 수익·안정성을 키운다.

2

데이터가 모델을 고른다 — 실데이터 성장곡선, W≈5.4만 건에서 모델 전환, full PR-AUC 0.820.

3

없던 데이터를 만든다 — 협상 (위험도→오퍼→수락→취소) 수집, 사전동의 구조로 법적 리스크 차단.

마무리 "우리는 두뇌(예측 엔진)를 만들었고, 그 두뇌는 호텔 데이터로 계속 자랍니다. 감사합니다."

예측만으로는 부족하다 — DSS 앱

확률 숫자만으로는
"매니저가 무엇을 해야 하는가"가 빠져 있습니다.

Tab 1 — 예약 우선순위 리스트
기존 예약 고위험 우선순위화 모델 예측 취소 확률 기준 정렬
SHAP 위험 요인 자동 표시
행 선택 → 개별 예약 SHAP 패널 연동
매니저의 조기 개입 의사결정 지원
Tab 2 — Flexi 라우팅 권장
신규 예약 Flexi 오퍼 권장 예약 정보 입력 → 취소 확률 실시간 출력
임계값 초과 시: Flexi 풀 라우팅 권장
할인율 자동 계산 + SHAP 위험 근거 제시
최종 결정은 매니저 승인 (GDPR Art.22)
핵심 발견 — DSS가 만들어내는 것
앱 도입 전: 취소 여부를 모르고 운영 → 사후 대응
앱 도입 후: 취소 위험 예약에 Flexi 오퍼 → 사전 합의
그리고 이 앱이 실제 호텔에 도입되면
지금까지 존재하지 않았던 데이터가 쌓입니다.
어떤 고객에게 어떤 조건으로 Flexi를 제시했고 고객이 수락했는지 / 거절했는지 → 이 label이 지금은 없습니다.

그 데이터가 지금 없다 — 구조적 부재

Kaggle 데이터에는
Flexi 오퍼 수락 여부 label이 없습니다.

어떤 산업 데이터를 찾아봐도 없습니다.
호텔들이 이 방식을 체계적으로 운영한 적이 없으니까요.
우리가 묻고 싶은 것: "얼마의 할인율에서, 어떤 고객이 Flexi를 수락하는가?" 데이터가 없다면? → 만들어야 합니다.
  • A
    무작위 파라미터 설정 할인율과 수락률을 임의로 가정 — "왜 이 값인가"를 방어하기 어렵습니다.
  • B
    실제 데이터 기반 LLM 에이전트 시뮬레이션 실제 예약 패턴을 에이전트의 뼈대로 사용합니다.
구조적 공백 — 기존 연구도 없음
전통 호텔 RM 시뮬레이션
몬테카를로 오버부킹 (IEEE 2015) — 모든 고객을 동일한 통계 분포로 모델링. 고객 이질성 무시, 할인 오퍼 반응 모델 없음.
LLM 소비자 시뮬레이션 (2025~)
AgentSociety, MALLES, LLM-Consumer — LLM 에이전트로 이질적 소비자 행동 포착. 그러나 호텔 Flexi 파라미터 검증에 적용한 사례 없음.
우리의 공백 지점 실제 호텔 예약 데이터셋에서 LLM 제로샷 예측 성능을 측정하고,
그 성능을 근거로 동일 데이터 기반 Flexi 시뮬레이션의
타당성을 주장하는 연결 구조 — 선행 연구 없음.

시뮬레이션 방어 논리 — 두 가지 주장

"LLM은 이 도메인을 아는가"
이론이 아닌 숫자로 답합니다.

Claim 1 — LLM 제로샷 취소 예측
훈련 없이 테스트셋에서 성능이 나오는가?
예약 데이터 7개 피처를 자연어로 변환 → LLM에 직접 입력
LLM이 Dummy를 유의미하게 넘으면:
"LLM이 이 도메인을 이해한다"는 경험적 근거
참고 선행 연구: TabLLM (arXiv:2210.10723), ProtoLLM (2025),
SHAP+LLM Faithfulness (arXiv:2512.00163)
Claim 2 — 게스트 아크타입의 효용
아크타입이 없을 때 vs 있을 때 비교
아크타입 없음 → 모든 세그먼트 비슷한 수락률
아크타입 있음 → 세그먼트별 분산이 뚜렷해짐
차이가 생기는 것 = 아크타입이 정보를 추가한다는 증거
참고 선행 연구: MALLES (arXiv:2603.17694),
WTP Hotel (arXiv:2602.09802), "Let It Go" (System Dynamics Review 2025)
예상 Q: "LLM 반응 = 실제 고객 행동이라는 근거가 있나?"
A: 직접 검증이 아니라 시뮬레이션입니다. 할인율 파라미터의 방향성(높은 할인 → 높은 수락률)이 도메인 상식에 부합하는지를 확인하는 것이 목적입니다. 정확한 수치 주장이 아닙니다.
